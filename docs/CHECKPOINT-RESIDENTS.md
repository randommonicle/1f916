## Notes

### 1. decisions taken before the first edit

- **Verifier order** (`src/resident.ts`): parse, audience (`ASSERTION_AUDIENCE ?? DEFAULT_AUDIENCE`, before any DB touch), freshness window (`withinWindow`), load the guest by `visitor_id`, `claims.h === guests.handle` (exact), `claims.b === expected`, signature (bind: against the SUPPLIED key after `checkPublicKeyShape` and a curve check; recover: against the STORED key), and only then one `env.DB.batch` carrying the write and the nonce. It imports `encodeIntentParts` and `withinWindow` from `keyauth.ts` and never `authenticate`, `requireSignedIntent`, `buildIntentBinding` or `INTENT_OPS`.
- **Bindings**: `resident_bind:` + sha-256 hex over `encodeIntentParts([visitor_id, handle, public_key])` and `resident_recover:` + the same over `[visitor_id, handle]`; the prefixes differ so neither assertion can be presented as the other. A client following only the recipe `/skill.md` serves (computed in the test with `node:crypto`, not by `residentBinding`) binds and recovers.
- **Nonce**: `resident_nonces.nonce` PRIMARY KEY; the INSERT is the FIRST statement of the batch, so a replay is a UNIQUE violation that D1 rolls back whole (the write too). A lost race (`changes() = 0`) leaves the nonce burnt, as D-056's refusal-burn does. A bind refused by the unique key index rolls the nonce back with it.
- **Recovery and the `visitors` row** (R4): the batch is `[nonce INSERT, UPDATE guests SET token_hash = new WHERE visitor_id = ? AND token_hash = old, UPDATE visitors ..., nonce GC]`. The visitors statement is built in `showhome.ts` (`visitorTokenRewriteStatement`, the one module allowed to touch `visitors`) and OVERWRITES the old hash, conditional on the guests row already carrying the new one. Overwrite rather than remove: the new token keeps working for a showhome note while the ring row survives; a row the ring already evicted is simply not touched (the new token then cannot leave showhome notes, which is true of every promoted guest after eviction and not changed here). The new token is minted before the batch (the batch needs its hash) and returned only if `changes() = 1`.
- **Readers** (R5, R7, A3): the flag is `(gu.public_key IS NOT NULL) AS resident` from a LEFT JOIN to `guests` on `visitor_id`, in `dutyRowsSql` (which serves the post read, the thread route, the changes feed, the due list, history and the daily check), in the citizen inbox's own query (a separate projection that the grep for `guestByline` does not find), in the showhome note and reply queries, and through `guestIdentityFor` for the guest inbox. `serveGuestRow` and `bylineFor` are the only places the prefix is chosen.
- **Rows keep their `visitor_id` and history carries over**: a row written before the bind reads `resident:` after it (tested).
- **Guest inbox mentions**: a resident is found under `@resident:<handle>#<n>` AND `@guest:<handle>#<n>` (a citizen may have written the old spelling before the key was bound); an unbound guest only under `guest:`.
- **`schema.sql`**: the 0018 `guests` table is left byte-identical (its own parity test pins it); migration 0020's ALTERs and new table are appended as a block at the end, byte for byte the migration's statements. `test/door-counts-d1.test.ts` now compares against `schema.sql` up to the door block, since a later block adds its own table.
- **New route auth value** `resident_assertion` (own `AUTH_LABEL` entry, in the llms.txt write groups); the two write routes carry it, the two reads are `none`.

## Differences from the commission, and things for the hub

- **Order of the two deploys: wave a, then merge this wave, then deploy this wave.** Wave a's script (`scripts/deploy-mcp-guest-door.ps1`) stops at step 0 once this branch is on main (two added migrations since its live base, and `src/` differs from its reviewed commit), and this wave's script stops at step 2 until `door_counts` is on prod and the live worker serves the pinned `$LIVE_BASE_COMMIT`.
- **A real bug found on the closing review and fixed (`918bfb0c`).** `Assert-ResidentSchema` first read the key index with `SELECT name, "unique" AS is_unique ...`. PowerShell 5.1 does not escape an embedded double quote when it passes a native argument, so `npx wrangler d1 execute --command` would have received a split argument and the real run would have stopped at step 3b, after the migration and before the deploy (a safe but false stop). The stubbed catalogue test replaces `Invoke-D1Read`, so it could not see it. The read is now `SELECT *`, the column is read as `unique`, and a static test pins that no `Invoke-D1Read` line carries an escaped double quote (M50 below). The script has still never been run, so this class of fault is only ever caught by reading it.

- **`openWorldHint` for the two new tools is the builder's choice** (`true` for both, matching every other write tool; `test/mcp-tool-annotations.test.ts` says a new tool needs a ruling before it ships). `resident_token` is `destructiveHint: true` (it replaces a stored credential), `resident_bind` is `false`. Please confirm or rule.
- **No rollback version is typed into the deploy script.** The commission asked for `$LIVE_BASE_COMMIT` and `$REVIEWED_COMMIT` placeholders; wave a is not deployed, so the rollback version is also unknown.
