## Findings

### MEDIUM

**M1. The D-076 aggregate reads the whole `ballots` and `council_ballots` tables once per citizen per request, so one public GET of `/api/citizens` reads 2,083 rows where the directory alone read 26, and the cost grows with the square of the society.**
`src/council.ts:266-281`: `(SELECT COUNT(*) FROM ballots b WHERE b.citizen_id = ct.id)` and `(SELECT MAX(cast_at) FROM ballots WHERE citizen_id = ct.id)` have no index with `citizen_id` leading (`schema.sql:243-245`: `idx_ballots_proposal_citizen(proposal_id, citizen_id)`, `prev_hash`, `hash`), so each is a full scan of `ballots` (or its covering index) for every id on the page; the same holds for `council_ballots` (PK `(motion_id, member_kind, member_id)`, `schema.sql:619`). Measured on Miniflare D1 over the real `schema.sql` and its indexes (`d1-cost-output.txt`):
- today-like (13 citizens, 65 ballots, 30 posts, 40 comments, 10 council ballots): the base directory SELECT reads **26** rows; the aggregate reads **2,083**.
- grown (100 citizens, 2,000 ballots, 300 posts, 1,000 comments, 200 council ballots): base **200**; aggregate **441,798** rows for one request.

Failure scenario: the project runs D1 on the free plan (project `CLAUDE.md`), whose daily read allowance is 5 million rows (Cloudflare's published limit; not re-fetched here, network barred), after which D1 refuses queries until 00:00 UTC. Today about 2,400 unauthenticated GETs of `/api/citizens` (or the `citizens` tool on `/mcp` or `/mcp/read`, both call `citizenDirectory`: `src/mcp.ts:840`, `src/mcp-read.ts:109`) spend the whole day's allowance and stop every D1 read and write for the society, including the paid register path's booking after an on-chain settle. That is well inside the Workers free plan's 100,000 requests a day. The class is not new (any public GET that reads whole chains, such as `/api/attest`, can be hammered; those other reads were NOT measured here, so no ratio to them is claimed), but this wave adds a read whose measured absolute cost is above, and because `ballots` grows with citizens x proposals the cost per request is quadratic: at the grown shape eleven ordinary reads a day would exhaust it, which is organic failure, not attack. `citizenDirectory`'s try/catch (`src/society.ts:2148-2156`, the catch logs and serves null) keeps the census up if the aggregate fails, but rows read are billed whether or not it succeeds.

Fix (code only, no migration): aggregate each table once per request with `GROUP BY citizen_id` (or `member_id`) restricted to the page's ids, and LEFT JOIN the grouped results to the `json_each` id list, so the cost is linear in the tables, not citizens x tables. Re-run `d1-cost.mjs` against the fix and keep the 1000-id and interleaving tests green. Alternatively Ben accepts today's 2,083 rows a request with a `DEFERRED-` flag at `citizenActivityPage` carrying a numeric trigger (for example, before 25 citizens or 500 ballots).

### LOW

**L1. The deploy script's rollback line understates the replay residual.** `scripts/deploy-hardening.ps1:297` says a nonce spent under the new worker is replayable on the old one "within its 120 s window". An assertion may be dated up to 120 s ahead (`src/keyauth.ts:242-244`, `Math.abs(now - issuedAt) <= 120 s`) and stays valid until `issuedAt + 120 s`, so the residual is up to 240 s after the spend, as the code comments at `src/society.ts:536-538` and `src/resident.ts:133-136` correctly say. Ben reads this line at the moment he is deciding a rollback. Change "within its 120 s window" to "for up to 240 s after it was spent". Text only; no test asserts the number (check before editing).

**L2. The deploy's own propagation overlap is the same residual as a rollback, and neither comment names it.** During the seconds a `wrangler deploy` takes to reach every location, old and new versions both serve. A captured assertion spent namespaced on the new worker (`c:<id>:<n>`) can be spent once more on an old-version instance, which inserts the raw `<n>` without colliding (proved on D1: `d1-proof-output.txt` P1 `old_worker_raw_after_namespaced_error: null`, the live base's plain INSERT of a nonce already spent as `c:9:<n>`). The reverse order is refused (raw first, then the CASE re-inserts raw and raises UNIQUE: P1). Bound: one extra spend of an already-captured, still-fresh assertion, only within the propagation seconds, and only for the same signed op (D-056 intent binding still holds). No code change needed; add "or while the deploy propagates" to the residual sentence in the two comments and the checkpoint.

**L3. The `NOT NULL constraint failed: <table>.nonce` branch of both refusal mappers is unreachable and would mislabel.** `src/society.ts:546`, `src/resident.ts:159`. The binds are never NULL (`?2` is a template string), and the columns are nullable (`schema.sql:442`, `:548`). The checkpoint says it is there so a future `NOT NULL` cannot turn a replay into a 500; the cost is that any NOT NULL failure on that column would be served as "already used". Harmless today. Note only.

Concurrent identical inserts: one PK, so one wins and the other raises.
- Raw row from the old worker: the CASE re-inserts the raw key and raises the same UNIQUE (P1 `raw_row_reinserted_error`, mapped). The row stays until `expires_at < now` and the assertion is valid only while `now <= issuedAt + 120 s = expires_at`, so a future-dated assertion accepted by the old worker is refused by the new one for its whole life (HW4).
