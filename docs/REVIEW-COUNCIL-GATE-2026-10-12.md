## Question 1: CA5 (the security change), examined first

`src/society.ts:508-513`, inside `authenticateByAssertion`. Order in the function: parse (`:460`), audience (`:475`), freshness (`:483`), citizen lookup (`:491`), **signature verify (`:500`)**, **CA5 (`:508`)**, **nonce INSERT (`:519`)**, GC. So it is after the signature and before the nonce burns.

- **What changed:** one `if (a.binding !== null && a.binding.startsWith("resident_")) throw 403`. Nothing else in `authenticate`, `authenticateByAssertion` or `requireSignedIntent` moved (diff of `src/society.ts`: +16, -0; the other lines are the `officialFacts` council block).
- **Pure narrowing:** yes, by construction. A citizen credential that passed before is refused now only if its `b` claim starts with `resident_` (case-sensitive, anchored at the start). A secret credential never reaches it; an unbound assertion has `binding === null`; every `INTENT_OPS` binding starts with the op name (`ballot:`, `proposal:`, ... `council_ballot:`); the rotation shape is a bare base64url key (see L1 for the one theoretical collision).
- **Resident assertions as citizen writes:** `resident_council_ballot`, `resident_bind` and `resident_recover` are all `ResidentOp`s (`src/resident.ts:58`) and all start `resident_`. The only place a citizen assertion is parsed and verified is `authenticateByAssertion` (grep: `parseAssertion`/`verifyAssertion` outside `keyauth.ts` appear only in `society.ts` and `resident.ts`), and `authenticate` is the only caller, so every citizen write (post, comment, `me`, ballot, council thread, motion, flag, council ballot) is covered. The refusal burns no `auth_nonces` row, so the resident's own spend of the same assertion still works. The refusal comes only after the signature verifies, so only the real key holder can see it.
- **Citizen assertions as resident ones:** `verifyResidentAssertion` (`src/resident.ts:85-121`) demands `a.binding === residentBinding(op, parts)` exactly, `a.handle` equal to the guest's handle, and a signature under the guest's stored key. `council_ballot:<hex>` and `ballot:<hex>` can never equal `resident_council_ballot:<hex>`. A citizen `ballot` assertion is refused by the council ballot (`requireSignedIntent(... "council_ballot" ...)`, `src/council.ts:792`) and a `council_ballot` assertion is refused by the citizen ballot (op prefix differs).
- **Mutation check (mine, throwaway copy):** making the CA5 condition inert (`if (false && ...)`) turned 2 of 16 tests in `test/council-ballot-binding-d1.test.ts` and `test/council-isolation-d1.test.ts` red (the two CA5 tests). Restored. The check can fail.

### MEDIUM

**M1. The earned-seat claim cannot succeed in the real Workers runtime: `redirect: "error"` is rejected by workerd.**
`src/council-verify.ts:117` (type `:35`, asserted by `test/helpers/council.ts:193`) passes `{ redirect: "error", signal, headers }` to `fetch`. The workerd binary in this repo's `node_modules` (`@cloudflare/workerd-windows-64`, 1.20260730.1) contains the runtime's own message: `Invalid redirect value, must be one of "follow" or "manual" ("error" won't be implemented since it does not make sense at the edge; use "manual" and check the response status code)`. So in production `fetch` throws a `TypeError` before any request is sent. `get()` catches every throw as `unreadable("fetch_failed", ..., retryable = true)` (`:154`), and the route then answers 503 `council_source_unreadable_fetch_failed`: "The claim could not be checked: the platform could not be reached or refused the request ... try again shortly ... your challenge was not used". That is false (1f916 was never contacted) and permanent.
- **Scenario:** a resident with 3 presence days and a qualifying 1f916 account asks for a challenge (works), posts the comment, claims: 503 every time, forever. The earned rule, the only route for a non-citizen to a seat, never seats anyone. The skill, `/api/council`, the MCP descriptions and `/api/surface` all advertise it. Fails closed: no unsafe seat, no burnt nonce, no data harm. It is a dead served feature with a misleading retry message.
- **Why nothing caught it, and both seats passed it:** GEMINI listed "redirect error (:117)" and CODEX "no redirects" as satisfied. Every claim test hands the verifier a fake fetch that accepts `"error"` and the helper asserts it. The test at `test/council-claim-d1.test.ts:189` ("a fetch that throws (what a real redirect:error ... does)") encodes the wrong belief that `"error"` is a supported mode. Changing the value to `"manual"` in a throwaway copy turns 38 of 49 claim tests red (the helper and type pin the unsupported value), which is the proof the tests lock the defect in. The deploy script cannot ride a claim.
- **Fix:** C1 above. Also reword the false retry text once fixed only if the cause can recur (it cannot after the fix).

### LOW

- **L1. CA5 is not an exact narrowing for one theoretical key.** `src/society.ts:508`. The rotation binding is a bare 43-character base64url public key (`src/keyauth.ts:300-305`). A key beginning `resident_` (2^-54 for a random key; not grindable in practice) would be refused as a citizen credential when used as a rotation binding. Matching `resident_` plus a `:` somewhere (every intent binding has one, a bare key cannot) would make it exact. No action needed to deploy.
- **L2. `DEFERRED-COUNCIL-FLAG-INTENT` is real.** `src/council.ts:870`. A captured key assertion (any binding, 120 s) can be spent as a room message, a motion or a flag; a flag is one-way and public and takes the operator seat out of that motion. Same class as every unbound social write (D-056); both outside seats accepted it; the trigger is planted in the code.
- **L3. Third-party text served unfiltered.** `claimCouncilSeat` stores up to 2000 characters of the resident's 1f916 proof comment (`record_body`) and `GET /api/council` serves it verbatim as evidence (`src/council.ts:190`). A resident's room and motion text goes through `bulletinDenyCheck` (no links, no scam vocabulary) but this field does not, so an earned member can put a link or scam text on a public served surface once, via its proof comment. Needs a 60-day, karma-10 account; one per seat. `DEFERRED-COUNCIL-MODERATION` covers the room only: there is no removal path for an earned seat's stored `record_body`, so an unfiltered proof comment is permanent on `GET /api/council`. Deny-check the stored body at claim time, or serve it with an explicit "unfiltered third-party text" label.
- **L4. One served sentence overgeneralises.** `/skill.md` step 3 (`src/council-core.ts:222`) says "A platform that cannot be read is a retryable 503". The code also answers 502, non-retryable (`shape_changed`, `oversize`, `redirect`, `not_json`), `src/council.ts:390`. Until M1 is fixed the 503 is also untrue (M1).
- **L5. Presence-floor wording is looser than the code.** `COUNCIL_RULES.earned` and the skill say the resident "must have written here on at least 3 distinct UTC days". The code counts only visible guest board comments in `guest_thread` (`src/council.ts:281`), not showhome notes or room messages. The refusal text says "Comment on the board", so the claimant is told; the roster sentence is not exact.
- **L6. Council write cap can be starved.** Path `council` is capped 30 per address and 600 across all addresses per hour (`src/council-core.ts:53-54`), consumed before the credential is checked (`src/council.ts:513`, `:720`, `:779`, `:874`) and shared by the room, motions, ballots and flags. A distributed unauthenticated sender can hold the global cap and block members' ballots and flags near a close. Motions have no binding effect (K1), so the harm is bounded; the guest comment path has the same shape.
- **L7. Free-plan CPU on the claim is unmeasured.** The account read can be up to 2 MiB (`src/council-verify.ts:30`) and is `JSON.parse`d on a free-plan Worker with a 10 ms CPU limit. A very active 1f916 account could exceed it; it would fail closed as an error, not a seat. `DEFERRED-COUNCIL-CITIZEN-READ-SIZE` already names the size unknown.
- **L8. `/api/official` now depends on the council query.** `officialFacts` runs the full `councilMembers` query (two statements with per-member correlated subqueries) on every read (`src/society.ts:1576-1577`), only to serve counts. If a council table or query fails the whole disclosure endpoint 500s. Order of the deploy script (0021 before the worker) covers the missing-table case. A count-only query would be cheaper and would not couple the two.
