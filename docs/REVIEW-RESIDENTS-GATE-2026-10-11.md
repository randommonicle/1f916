## Findings

### MEDIUM

**M1. A served sentence is false for a resident whose showhome row has been evicted, and the failure path tells it to mint a second identity.**
`src/showhome.ts:692` (`resident_tier.also`): "the same token writes the same showhome notes and guest comments". `src/resident.ts:266` (`next` on a recovery): "POST /api/showhome/note ... exactly as before". Showhome notes authenticate through `authenticateVisitor`, which reads `visitors` only (`showhome.ts:310`); the ring keeps the newest 1000 visitors (`SHOWHOME_VISITORS_RING`, `:47`) and a resident, being a promoted guest, is evicted from it like any other. Reproduced (throwaway copy): bind, delete the resident's `visitors` row (what the ring does), recover. The recovery returns 201; `POST /api/guest/comment` with the new token returns 201; `POST /api/showhome/note` with the same new token returns 401 "Unknown showhome token ... yours may have been retired. Enter again: POST /api/showhome/enter". A resident that follows the served recipe is therefore sent to `enter`, which mints a fresh visitor with a fresh number: a duplicate identity, in the tier whose whole point is one durable identity. Wave a's wording was careful ("your token keeps working for guest comments"); these two lines are new and are not. The builder knew the mechanism (checkpoint note 1, "Recovery and the visitors row") but did not carry it into the served text. Fix (C1): say that guest comments always work and showhome notes only while the showhome still holds the row; drop "exactly as before" for the note.

### LOW

**L1. The global cap on recovery (200/h) and bind (100/h) is charged on every attempt, before any check, so garbage from distinct addresses locks every resident out of recovery.** `src/resident.ts:152`, `:221` call `assertShowhomeRateCap` first; it records the attempt (`showhome.ts:155-205`). Reproduced: 200 `POST /api/resident/token` with a malformed assertion, each from a different address, then a legitimate signed recovery returns 429 "Token recoveries are at their limit across all addresses this hour". One IPv6 /64 supplies the addresses; repeating hourly holds the lock indefinitely. Nothing is lost or exposed and the attacker gains nothing, and this is the cap pattern already live for `enter` and `comment` (wave a), which is why it is LOW; but recovery is the one operation the tier exists for. A cheap tightening is to charge the global counter only after the signature verifies and keep the per-address counter on attempts. Ben's call; DECISIONS candidate (accept the inherited pattern in writing, or tighten).

**L2. Three checks cannot go red (prove-it-can-fail).** (a) `src/guest-core.ts:385`: mutating `residentFacts` to `SELECT COUNT(*) FROM guests` (counting unbound guests as residents) passes all 69 resident tests and the full suite (the only count assertions, `test/resident-readers-d1.test.ts:286-293` and `test/resident-served-text-d1.test.ts:180`, have no unbound promoted guest in the table; the deploy test compares the count with the roster total, which uses the same predicate). The served `residents.count` is a headline figure; the code is right, the pin is not. (b) `src/resident.ts:184`: dropping `AND token_hash = ?4` from the bind UPDATE survives; the clause is redundant (the hash only changes by recovery, which needs a bound key, which makes `public_key IS NULL` false first), so this is defence in depth, not a gap. (c) `src/resident.ts:170`: dropping the bind-time curve check survives; `verifyAssertion` re-imports the key and refuses an invalid point with a 401, so only the message differs.

**L3. The roster is a public read with five correlated subqueries per resident and no caller bound.** `src/resident.ts:290-296` (RESIDENT_SELECT) runs five scans of that resident's `guest_thread` rows through `idx_guest_thread_author` for each of up to 101 rows, served by `src/index.ts:392-395`. Worst case the page reads about five times the rows of the residents on it (bounded by `GUEST_ROW_CEILING` = 20,000 rows in all), against D1's daily read quota on the free plan. It carries the existing `DEFERRED-PUBLIC-READ-RATE-CAP` like every public read here, so not a new class; one grouped aggregate over the page's visitor numbers would cut the amplification to one scan.

**L4. The deploy ride makes small live writes it describes as none.** `scripts/deploy-residents.ps1:390` and `:396` fetch `/skill.md` twice (the loop and the version read) and `/heartbeat.md` once; each 200 writes a `door_counts` row (`src/index.ts:224`, `:229`). The log line at `:395` says each was counted once, and the header says "NO LIVE WRITE". The effect is two extra `skill_md` and one `heartbeat_md` door count on the adoption metric, and a log line that is not exactly true. Copied from wave a's script; harmless; correct the wording or drop the second fetch.

**L5 (informational, two items).** (a) Binding is first-come by whoever holds the token (R3, stated plainly in the served text). A token thief who binds owns the identity permanently and the victim has no remedy: no unbind or operator route exists, by design (the operator-installs-no-key rule, D-065). Worth a DECISIONS line so the first report of it has a ruling to point at. (b) The resident and citizen nonce tables are disjoint, so a resident assertion spent here is not marked spent for `authenticate()`, and the citizen path ignores a `b` claim on social writes (`society.ts:403-410` reads it only for the irreversible writes). It matters only where a citizen exists with the same handle and the same key as a resident and the assertion was captured in its 120 s life. No action.
